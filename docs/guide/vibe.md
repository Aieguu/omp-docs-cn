# Vibe 模式

## 从一个对话中指挥多名工作者

Vibe 模式适合那些能从委派中受益的工作：一个前端与后端改动相互独立的功能、一次迁移加审查，或者可以拆分成文件互不重叠（file-disjoint）工作线的大型清理。你的主 omp 会话会变成一个**指挥者**（director）。它负责阅读并核实仓库，而持久化的工作者（worker）则负责搜索、编辑、运行命令和构建。

可以在同一条命令中带上任务开始：

```
/vibe Split this release into independent workstreams. Have a fast worker update the mechanical call sites and a good worker review the migration and compatibility risks. Verify both before reporting done.
```

也可以先进入模式，再描述工作：

```
/vibe
```

模式激活期间，状态行会显示 **Vibe**。当你准备离开时，再次运行 `/vibe`；omp 会停止剩余的工作者，并恢复你进入之前已启用的工具。

Vibe 模式会带来协调、模型用量与监督方面的额外开销。对于小型的串行编辑，普通的 omp 提示词通常更简单。

## 选择 `fast` 或 `good`

你不需要另开终端，也不需要提供机器可读的请求。用日常语言告诉指挥者你想要哪种工作者：

| 工作者 | 最适合 | 典型指令 |
| --- | --- | --- |
| `fast` | 机械性的、规格明确的、大批量的工作：重命名、简单直接的测试、样板代码、数据收集，以及套用已定好的模式。 | “用一名 fast 工作者更新 `packages/ui` 里的所有调用方；不要改动公开 API。” |
| `good` | 设计、调试、审查、有风险的改动、多文件重构，以及判断力比延迟更重要的工作。 | “让一名 good 工作者追踪这个竞态，提出最小的源码修复，并用现有的复现步骤加以验证。” |

fast 工作者并不只是一个优先级较低的任务：它通常使用你的 small、低延迟模型角色。good 工作者通常使用你的 task/强模型路径。如果 fast 工作者停滞不前，或遇到了架构层面的决策，请让指挥者把该决策或审查交给 good 工作者，而不是反复重启同一段工作。

每个工作者都有自己的对话，并且会记住后续指令。让一名工作者专注于一条工作线，这样其上下文才能保持有用。工作者启动时并不携带指挥者的对话，因此指挥者必须给每一名工作者一份自包含的任务简报。

## 给出能够独立成功的工作线

一条有用的首个提示词会写明所有权、边界与证明：

```
Coordinate these in parallel:

1. Fast worker: own `packages/parser/src/` and update the mechanical API call sites. Preserve behavior and run the parser's focused tests.
2. Good worker: own `packages/server/src/` and design the compatibility change. Do not edit parser files. Exercise the failing request after the fix.
3. When both finish, read their changed files, check that the contracts agree, and have the good worker review the integration.

Do not let both workers edit the same file. Stop and ask me if the shared interface must change.
```

只要相关，就应包含以下细节：

*   该工作者拥有的文件或子系统；
*   预期结果与可观察的验收标准；
*   不得更改的 API、格式或行为；
*   能证明结果的命令或场景；
*   明确的非目标与安全边界；
*   另一条工作线将要消费的契约。

并行工作者共享同一个工作树，除非指挥者选择了另一种受支持的隔离策略。两个工作者编辑同一个文件时可能互相覆盖或冲突。请优先采用文件互不重叠的所有权划分，在派发之前先确定共享接口，并指定一名工作者来整合任何无法避免的共享文件。

## 监督工作

工作者运行期间，你可以继续与指挥者对话。派发是异步的：指挥者可以启动另一条独立的工作线，而不必等待第一条完成。

有用的提示词包括：

```
Show me every Vibe worker, its fast/good tier, current state, model, queued follow-ups, and latest activity.
```

```
Steer the parser worker now: preserve the legacy error code and add a boundary case before continuing.
```

```
When the server worker becomes idle, ask it to review the parser worker's final diff. Keep it in the same worker session.
```

```
Stop the docs worker; that workstream is no longer needed.
```

在工作运行期间发送的纠正消息，会尽可能被引导进正在进行的轮次。如果工作者无法立即接受，omp 会将其排入队列作为下一轮。空闲的工作者则会以这条后续消息开始新一轮。你无需判断具体属于哪种送达情形。

工作者的结果会自动返回到指挥者对话。可见的工作者视图会区分正在启动、运行中、空闲或已死亡（dead）的工作者，并显示它们的层级（tier）、轮次数、排队的工作、解析后的模型以及最近的活动。已完成的轮次还会显示活动与耗时。只要工作者名称或状态不清晰，就再次索要名册。

不要把“工作者已完成”当成“任务已验证”。让指挥者：

1.   阅读工作者声称已更改的文件；
2.   将结果与你最初提出的约束进行比对；
3.   化解跨工作线的假设分歧；
4.   把纠正消息发回同一名工作者；
5.   在报告完成之前运行或委派验收场景。

在 Vibe 模式下，指挥者刻意配备了一套以读取为主的工具集。它负责核实与协调；工作者执行修改和命令。

## 停止工作并安全离开

这里有三种不同的控制手段：

*   **引导某一名工作者：**描述纠正内容并指明该工作者或工作线。其持久化的对话会被保留。
*   **停止某一名工作者：**说“停止 `<name>` 工作者”。其活动轮次和排队的后续消息会被取消，但其他工作者继续运行。
*   **退出模式：**运行 `/vibe`。必要时 omp 会中止指挥者的活动轮次，停止所有剩余的 Vibe 工作者并将它们记录为终态，移除 Vibe 专属的控件，并精确恢复进入 Vibe 之前的工具集。

退出是安全的完成边界。不要想当然地认为空闲的工作者已经离开：空闲意味着准备好开始下一轮，而不是已终止。反过来，有意执行的 `/vibe` 退出对那一批工作者范围而言是最终的：重新进入会启动新的工作者，而不是复活退出时被终止的工作者。

如果你打断了当前的指挥者响应，Vibe 模式本身仍然保持开启。查看 **Vibe** 状态指示器，索要工作者名册，然后要么继续监督，要么运行 `/vibe` 执行完整关闭。

## 持久化、恢复与会话变更

Vibe 模式与工作者的生命周期记录随父会话一起存储。当你重新打开一个当前模式为 Vibe 的已保存会话时：

*   已完成的工作者对话会以空闲/已停放工作者的形式连同其子转录一起返回；
*   指挥者可以用另一条自然语言指令继续这些工作者；
*   进程停止时仍在运行的工作会被标记为已中断，并且**不会**自动重启；
*   被显式停止的工作者，或因有意退出 Vibe 而停止的工作者，保持终态。

重启之后，先从这条开始：

```
List the restored Vibe workers. Summarize their last completed work, identify any turn interrupted by the restart, and wait for my approval before continuing it.
```

切换会话时，当前会话的 Vibe 工作者会被静默（quiesce），并在适用时恢复目标会话所记录的模式与工作者范围。但是，在 Vibe 处于活动状态时，创建或结构性迁移会话的操作会被阻止：启动新会话、分叉、移动和交接都要求你先运行 `/vibe`。这可以防止工作者与拥有它们的父会话脱离。

计划模式与目标模式和 Vibe 模式互斥，即使计划或目标处于暂停状态也不例外。在 `/vibe` 之前先退出已有模式；在进入 `/plan` 或 `/goal` 之前先退出 Vibe。Vibe 活动期间，重置式的循环也不可用。

## 模型与成本

fast 与 good 工作者会各自独立地发起模型请求，因此并发的工作者可能同时消耗 token。它们的成本会叠加在指挥者的模型用量之上。对于紧密耦合的工作，请使用更少的持久化工作者；停止已完成的工作者；当 fast 工作者已经足够时，把 good 工作者留给设计或审查。

默认值遵循 omp 正常的工作者路由：

*   `fast` 使用内置的 `sonic` 工作者，通常经由 small 模型角色解析；
*   `good` 使用内置的 `task` 工作者，通常经由 task 角色或活动/默认模型回退来解析。

在角色中设置具体的选择器，并在 [`~/.omp/agent/config.yml`](./settings.md) 中把这两个工作者定义路由过去：

```
modelRoles:
  fast_worker: openai/gpt-5-mini
  good_worker: anthropic/claude-sonnet-4-5:high

task:
  agentModelOverrides:
    sonic: "@fast_worker"
    task: "@good_worker"
```

这样可以让面向用户的 `fast` 和 `good` 选择保持稳定，同时让你能在一处更改 Provider 或模型。常规的重试与回退设置同样适用于工作者请求。当路由结果出乎意料时，让指挥者显示解析后的模型。在运行期间或结束后，使用 `/stats` 检查会话与工作者成本；`/usage` 报告的是 Provider 账号限额，而不是单条 Vibe 工作线的成本。

## 安全与权限

工作者是完整的编码 agent：它们可以读写文件、运行命令，并使用其任务简报所需的其他已启用能力。指挥者的只读姿态并不会让工作者变成只读。

工作者在派发之后以无头（headless）方式运行，因此不要指望它执行的每条命令都会弹出交互式确认。你配置的每工具策略仍然生效。对于工作者绝不可使用的能力，请使用显式的 `deny` 策略；把凭据和敏感路径排除在其范围之外，并在提示词中给出它自己的边界。`tools.approval` 与审批模式请参见[设置](./settings.md)。

在敏感代码上使用 Vibe 之前：

*   选择已获准接收仓库内容的模型与 Provider；
*   按工作线拆分访问权限，避免在提示词中放入不必要的秘密；
*   在配置中禁用危险的工具或命令类别，而不是只依赖文字描述；
*   要求聚焦的验证，并由指挥者做最后的通读；
*   一旦工作者的活动或输出不再符合任务简报，立即停止它。

同时启动多个工作者，既增加了可以改动工作树的行为者数量，也增加了编辑相互重叠的概率。在高并发运行之前，请提交或以其他方式保存重要的工作，但不要让多名工作者并发地操作同一个 Git 状态。

## 故障排查

*   **`/vibe` 提示先退出 Plan 或 Goal** — 其中包括处于暂停状态的模式。先彻底退出那个模式，然后再次运行 `/vibe`。
*   **Vibe 指示器亮起，但没有工作开始** — 向指挥者给出明确的工作线、层级、文件、约束和验收检查。如果按你的审批模式派发需要授权，请批准或拒绝可见的请求。
*   **工作者用错了模型** — 索要解析后的工作者模型。检查 `task.agentModelOverrides.sonic`（对应 fast）和 `.task`（对应 good），然后确认每个被引用的 `modelRoles` 选择器都存在、其 Provider 已启用且认证可用。新启动的工作者会采用修正后的路由。
*   **工作者处于空闲状态** — 空闲是健康且持久的：它完成了上一轮，正在等待。把下一条指令发给同一名工作者；如果工作线已经完成，就停止它。
*   **纠正消息没有改变当前步骤** — 它可能因为该轮次当时无法被引导而被排入队列。索要该工作者排队的后续消息，让当前轮次平稳结束；如果继续下去不安全，就停止它。
*   **工作者已死亡或找不到** — 向指挥者索要当前会话的名册。工作者的所有权与其父会话绑定；被有意停止的工作者无法恢复。需要时，用一份全新的自包含简报启动新工作者。
*   **omp 在轮次期间重启** — 重新打开父会话并索要已恢复的工作者。在明确继续之前，先检查被中断工作者的转录与仓库状态；omp 不会重放被中断的轮次。
*   **两名工作者更改了同一个文件** — 停止后续相互重叠的工作，选定一名整合负责人，检查实际的文件，并让该负责人对照两条工作线的契约来调和这些更改。不要再发起新的相互重叠的编辑。
*   **工作者似乎卡住了** — 索要其最近的活动，并引导它走向更小的下一步。如果它仍然没有进展，就停止它，并把剩余工作连同目前收集到的证据重新委派给一名 good 工作者。
*   **你无法启动、分叉、移动或交接会话** — 运行 `/vibe` 退出并停止其工作者范围，然后重试该会话操作。
*   **你打断了 omp，不确定哪些内容保留了下来** — **Vibe** 徽标表示模式仍然处于活动状态。继续之前先索要名册，或运行 `/vibe` 进行确定性的关闭。
